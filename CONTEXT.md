# Muzz Chat — Domain Glossary

## User
A participant in the conversation. Two fixed users exist: `ME` (the local user) and `SARAH` (the other participant). Each has a stable UUID and a display name. No authentication exists — users are hardcoded constants in `chat/domain/model`.

## Chat
A conversation between Users, identified by a server `chatId`. Every Message belongs to exactly one Chat, and its `seq` counts within that Chat. The app opens a single Chat, with Sarah. Use "Chat" and `chatId`, not "conversation" or `conversationId`.

## Message
A unit of communication between two Users, in one Chat. A sealed class with two kinds, `Message.Pending` and `Message.Confirmed`. Both have a `clientMessageId`, a `chatId`, a `senderId` (UUID), a `Content` and a `timestampMillis` (epoch millis, so always UTC). It is identified by its `senderId` and `clientMessageId` together, from the moment it is sent. Has no edit flag and no delete flag — these are deliberate omissions for this scope. A domain model, stored as `MessageEntity` in one Room table in `chat/data`. See [ADR-0001](docs/adr/0001-repository-dual-datasource-echo-pattern.md).

## Pending Message
A `Message.Pending`: a message this device has sent that the server has not confirmed yet. Its `timestampMillis` is the device time. It has no `serverMessageId` or `seq`, so it sorts after every confirmed message. Shown as `SENDING`.

## Confirmed Message
A `Message.Confirmed`: a message the server has stored. Has the `clientMessageId` it was sent with, and the server's `serverMessageId`, `seq` and `timestampMillis`. Shown as `SENT`.

## clientMessageId
A UUID generated by the sender's device for each message it sends. The server stores it and returns it on every message, from any sender, so every message has one. It is unique per sender, not across senders, so a message is identified by its `senderId` and `clientMessageId` together. That pair is the message's Room primary key and its key in the UI, so the key stays the same from pending to confirmed. It also lets a resend be recognised by the server instead of stored twice.

## serverMessageId
The server-generated ID of a confirmed message: an opaque UUID. It identifies the message on the server and says nothing about its order. The device never generates it. Not to be confused with `clientMessageId` or `seq`.

## seq
The position of a confirmed message in its Chat, assigned by the server: 1 for the first message, then every next number, with no holes. It alone decides the order of confirmed messages and is the paging cursor, so a missing number is a missing message, and `seq` 1 is the start of the history. A deleted message would keep its `seq` and lose only its content, which is out of scope. `timestampMillis` is never used for order.

## History page
One response from the server's message history: up to `limit` confirmed messages, a `nextCursor` (the `seq` to continue from in the same direction) and `hasMore` (whether more messages remain in that direction). A page is requested before a `seq` (older messages), after a `seq` (newer messages), or with no cursor (the newest messages).

## Chat sync state
What the device knows about a Chat's history, stored per Chat beside its messages: the `seq` to continue older history from, the newest `seq` up to which stored history has no gaps, and whether the start of the history has been reached. It moves only when a page or message is written, in the same transaction.

## Catch-up
Fetching the history pages after the newest gap-free `seq` until the server reports `hasMore = false`. It runs when a Chat is opened, and when an incoming message skips a `seq`.

## Echo
The server's stored copy of a message this device sent, returned with its `clientMessageId`, both as the send response and on the incoming stream. Whichever arrives first confirms the message: the repository updates the pending row with the same `senderId` and `clientMessageId` in place, with the server's `serverMessageId`, `seq` and `timestampMillis`. The second copy writes the same values, so it changes nothing.

## MessageWithNext
A row of the paged message list: a `Message` together with the `senderId` and `timestampMillis` of the next message in conversation order, or nulls when there is none. Computed by the paged Room query and never stored. It exists because the bubble tail depends on the next message, and paging maps one row at a time.

## Content
The payload of a Message. Has a `ContentType` (currently `TEXT` only) and a `value` (String). Modelled as a data class to allow future content types without changing the Message schema.

## MessageDirection
Whether a rendered message is `OUTGOING` (sent by ME) or `INCOMING` (sent by SARAH). A UI-layer concept derived from comparing `senderId` to `Users.ME.id`. Not to be confused with delivery status.

## ChatItem
A UI-layer model representing one renderable row in the message list. Either a `Message` (with `messageId`, `direction`, `content: String`, `timestampMillis`, `isGrouped`, `deliveryStatus`) or a `TimestampHeader` (with a pre-formatted `label` and a `key`). A message's `messageId` is its `senderId` and `clientMessageId` joined, so it stays the same from pending to confirmed. A header's `key` is derived from the message below it. Built by `ChatItemMapper`.

## TimestampHeader
A `ChatItem` variant rendered as a centred date/time divider. Inserted above a message when the gap from the older message exceeds one hour, or when it is the oldest message in the conversation. The format depends on how many calendar days ago the message was sent, in the device's time zone: today `11:59`, 1–6 days ago `Thursday 11:59`, otherwise `12 Mar 2026 11:59`.

## Grouped Message
A `ChatItem.Message` where `isGrouped = true`. Occurs when the next message is sent by the same User AND within 20 seconds. Rendered with no tail on the bubble and the small gap below it, because the next bubble continues the run.

## ChatItemMapper
A pure Kotlin object (no Android dependencies) holding the display rules, each looking at one message and one neighbour. `toMessageItem` builds a `ChatItem.Message` and computes `isGrouped` from the next message. `headerAbove` returns a `TimestampHeader` when one belongs above a message, choosing its `DateTimeFormat`. Paging applies them with `map` and `insertSeparators`. Date arithmetic and formatting are done by `calendarDaysBetween` and `formatUtc` in `utils`. The primary unit under TDD.

## ChatUiState
The state object the ViewModel exposes to the UI via `StateFlow`. Contains `inputText: String`. The message list is exposed separately as `Flow<PagingData<ChatItem>>`, because paged data is a stream. No loading or error state — deliberate trade-off documented in decisions log.

## MessageDeliveryStatus
The delivery state of a message, as shown in the UI. Follows from the message type: `Pending` is `SENDING` and `Confirmed` is `SENT`. `FAILED` and `RETRYING` are reserved for future error handling, and will be states of a pending message.

## ChatRepository
The domain interface for working with messages. Exposes `getMessages(chatId): Flow<PagingData<MessageWithNext>>`, `syncIncomingMessages(chatId)` and `sendMessage(message: Message.Pending)`. `syncIncomingMessages(chatId)` stores that Chat's messages from `ChatRemoteDataSource` until its caller cancels it, ignores other Chats' messages, and runs a catch-up when a message skips a `seq`. `ChatRepositoryImpl` in `chat/data` implements it and is the single ingestion point for all messages.

## SendMessageUseCase
Trims and validates message text, ignores blank input, and builds a `Message.Pending` for a Chat, with a new `clientMessageId` and the device time, before passing it to `ChatRepository`. The only use case, because the other operations have no logic of their own.

## ChatRemoteDataSource
The interface representing the remote messaging service. Exposes `sendMessage(chatId, dto): Result<MessageDto>` for outgoing messages, `fetchMessagesBefore(chatId, beforeSeq: Long?, limit)` and `fetchMessagesAfter(chatId, afterSeq: Long, limit)`, each returning a `Result<MessagePageDto>` history page, and `incomingMessages(): Flow<MessageDto>` for the incoming stream of every Chat, one WebSocket in production. The order it delivers messages in does not matter, because Room orders them. `MockChatRemoteDataSource` implements this using `MockData`, echoing sent messages back on `incomingMessages()` and answering `fetchMessages`, each after a ~200ms simulated network delay.

## ChatLocalDataSource
The interface over Room, and the single source of truth for the UI. Stores pending and confirmed messages in one table, confirms a pending message in place when its echo arrives, keeps each Chat's sync state, and exposes the paged `MessageWithNext` query for one Chat, newest first: pending messages by device timestamp, then confirmed messages by `seq`.

## MessageRemoteMediator
The Paging 3 `RemoteMediator` in `chat/data`, one per open Chat. When the Chat opens, it runs a catch-up, or fetches the newest page when nothing is stored. When the user scrolls past the stored history, it fetches the page before the sync state's oldest `seq`. History is complete when the server reports `hasMore = false` for older messages. See [ADR-0003](docs/adr/0003-cursor-paging.md).

## MockData
The fake server's messages, in `chat/data/mock/`. Holds a pre-written conversation from `assets/mock_messages.json`, all in the one Chat that `MainActivity` opens, numbered by `seq` from 1 and large enough to fill several pages, plus any messages sent since the app started. Every message has a `clientMessageId`. It gives each sent message a random UUID `serverMessageId`, the Chat's next `seq` and the server time, returns the stored message when the same sender resends a `clientMessageId`, and answers history pages by `seq` with `nextCursor` and `hasMore`. Only `MockChatRemoteDataSource` uses it.
